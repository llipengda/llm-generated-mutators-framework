                  Atlas Task Protocol，版本 1（ATP/1）

摘要

   Atlas Task Protocol（ATP/1）是一种用于设备控制、内部服务编排和边缘
   状态同步的二进制应用层协议。它定义身份建立、资源读写、命令执行、主题
   订阅、异步事件、幂等请求和应用错误。ATP/1 可以运行在 TCP 或 UDP 之上；
   TCP、UDP 仅负责承载 ATP 协议数据单元（PDU），不决定业务语义。

   ATP/1 使用二进制固定头和 TLV 正文。TCP 与 UDP 使用逐字节完全相同的
   PDU 格式，不增加或删除任何承载专用字段。本协议通过预共享密钥和消息认证
   码验证对端身份及报文完整性，但不加密业务内容。

状态与规范性用语

   本文档是私有部署规范。MUST 表示必须满足，MUST NOT 表示绝对禁止，SHOULD
   表示除非有充分理由否则应满足，SHOULD NOT 表示除非有充分理由否则不应采用，
   MAY 表示可选。无法安全解释的报文必须被拒绝，并且不得触发业务操作。

1. 适用范围与设计原则

   ATP/1 面向以下私有应用：控制器读写设备状态；边缘代理调用设备动作；内部
   服务交换小型结构化数据；客户端订阅状态变化。典型资源包括
   /lights/lobby、/devices/7/config 和 /jobs/42/state。

   协议遵循以下原则：

   a. 应用语义独立于承载层。同一业务请求在 TCP 和 UDP 中使用相同的 PDU。
   b. 每个请求具有明确的 Transaction-ID，可关联响应并抑制重复执行。
   c. 状态资源具有版本号，可执行条件更新并发现并发冲突。
   d. 所有会话内 PDU 均经过认证；解析者在认证前不得执行业务操作。
   e. 未识别的可选 TLV 可以跳过，未识别的操作必须返回明确错误。
   f. 解析失败采用安全关闭或静默丢弃，不猜测发送者意图。

   ATP/1 不提供传输层拥塞控制、数据流传送、大文件分块、跨资源事务、持久消息
   队列或内容加密。需要这些能力的部署必须在 ATP/1 外部提供。

2. 术语和数据表示

   PDU：一条完整 ATP 消息，由固定头和 TLV 正文组成。
   客户端：发起 HELLO 并创建应用请求的一方。
   服务端：接受 HELLO、维护会话并处理请求的一方。
   会话：由 Session-ID 标识、持有独立会话密钥的一段通信关系。
   资源：由绝对路径命名、带值和版本号的应用状态。
   操作：REQUEST 希望服务端执行的应用行为。
   主题：事件发布和订阅所使用的分层名称。
   幂等：同一请求被接收多次时，业务效果与只接收一次相同。

   所有多字节整数采用无符号大端表示。I64 是有符号二进制补码大端整数。
   UTF-8 字符串不得包含 NUL 字节，必须是最短合法编码。除明确允许外，长度均
   以字节计而不是字符计。十六进制仅用于本文示例，不是线上文本格式。

3. 总体通信模型

   一次正常会话经历以下阶段：

       未建立 --HELLO/HELLO_OK--> 已建立 --REQUEST/RESPONSE--> 已建立
          |                           |                |
          | 握手失败                   | GOODBYE        | 会话超时
          v                           v                v
        已关闭                      已关闭           已失效

   客户端在会话建立前只能发送 HELLO。服务端在会话建立前只能发送 HELLO_OK 或
   丢弃无效报文。建立后，客户端可以发送 REQUEST 或 GOODBYE；服务端可以发送
   RESPONSE、ERROR、EVENT 或 GOODBYE。收到 GOODBYE 后不得再在该会话中创建新
   请求。失效 Session-ID 不得被重新分配给新会话。

   每个 REQUEST 必须获得一个 RESPONSE 或 ERROR，除非承载连接已经关闭、会话
   已失效或 UDP 响应丢失。EVENT 是服务端主动发送的消息，不对应 REQUEST。

4. TCP 与 UDP 承载绑定

   ATP/1 只定义一种线上 PDU。相同消息无论经 TCP 还是 UDP 发送，从 Magic 到
   最后一个 MAC 字节必须完全相同。承载绑定仅规定如何从承载中取出完整 PDU，
   不得给 PDU 添加长度前缀、UDP 专用头、TCP 专用头或不同的校验字段。

4.1 TCP

   TCP 字节流直接串联完整 ATP PDU，不使用任何额外长度前缀。接收端先累积并
   读取固定的 30 字节头，验证 Magic、Version、Header-Length 和 Header-CRC，
   再从头中的 Body-Length 得到剩余字节数，并读取恰好 Body-Length 字节。由此
   得到的 30 + Body-Length 字节就是一条完整 PDU。

   一次 recv 返回的数据可能不足固定头、只包含部分正文、恰好包含一条 PDU，
   或同时包含一条 PDU 的尾部和下一条 PDU。实现必须维护接收缓冲区，不得把
   recv 调用的返回边界当作消息边界。解析完一条 PDU 后，缓冲区中的后续字节
   从下一条 PDU 的 Magic 开始继续解析。

   Body-Length 使 TCP 可以划分消息，但该字段同样存在于 UDP PDU 中，因此不
   构成 TCP 专用格式。Body-Length 超过本地上限、固定头无效或认证失败时，
   接收端 MUST 关闭 TCP 连接。客户端可以连续发送多个请求；服务端可以按不同
   顺序返回响应，客户端必须使用 Transaction-ID 关联请求和响应。

4.2 UDP

   每个 UDP 数据报必须恰好包含一条完整 PDU。数据报的第一个字节就是 PDU 的
   Magic，不存在 UDP 专用封装。数据报长度必须等于 Header-Length + Body-Length。
   建议完整数据报不超过
   1200 字节，以降低底层网络分片概率。ATP/1 不定义应用分片；超过本地 UDP
   上限的业务值应改用 TCP 或外部对象存储。

   UDP 来源地址不是身份依据。只有有效 MAC 才能证明发送者持有密钥。服务端可
   将会话与最近验证成功的来源地址关联；若来源地址改变，服务端 MAY 接受具有
   有效 MAC 的新地址，但应记录安全事件。

   无效 Magic、长度、CRC、Session-ID 或 MAC 的 UDP 数据报 MUST 静默丢弃，
   以避免反射攻击。仅对已认证、结构有效的请求返回 ERROR。

5. PDU 固定头

   固定头为 30 字节：

   偏移  长度  字段                 说明
   ----  ----  -------------------  ----------------------------------------
     0     2   Magic                固定为 0x41 0x54，即 ASCII "AT"
     2     1   Version              固定为 1
     3     1   Kind                 消息种类
     4     2   Flags                标志位
     6     2   Header-Length        固定为 30
     8     8   Transaction-ID       请求/响应关联标识
    16     8   Session-ID           会话标识；HELLO 中为零
    24     4   Body-Length          TLV 正文总长度
    28     2   Header-CRC           固定头校验值

5.1 Kind

   1 HELLO：客户端发起握手。
   2 HELLO_OK：服务端接受握手。
   3 REQUEST：客户端请求应用操作。
   4 RESPONSE：服务端成功完成操作。
   5 EVENT：服务端向订阅者发送异步事件。
   6 ERROR：服务端拒绝请求或操作失败。
   7 GOODBYE：任一方正常结束会话。

   其他 Kind 为保留值。会话建立后收到未知 Kind，服务端返回 UNKNOWN_KIND；
   会话建立前或 UDP 中无法认证时静默丢弃。

5.2 Flags

   bit 0 ACK_REQUIRED：发送者需要明确响应。所有 REQUEST 均 MUST 置 1，与承载
   类型无关。bit 1 RETRANSMIT：该 PDU 是同一 Transaction-ID 的重传。
   bit 2 FINAL：发送者不会再发送与本事务相关的消息，ATP/1 基础操作均置 1。
   bit 3 至 bit 15 保留，发送者 MUST 置零。接收者发现保留位非零时返回
   BAD_FLAGS；未认证 UDP 报文仍静默丢弃。

5.3 标识和长度

   Transaction-ID 必须是非零 64 位数。客户端应从安全随机源生成；在同一会话
   中不得重复用于不同请求。HELLO_OK 必须复制 HELLO 的 Transaction-ID；
   RESPONSE 和 ERROR 必须复制 REQUEST 的值。EVENT 的 Transaction-ID 由服务端
   生成且与该会话中尚未完成的事务不同。

   Session-ID 由服务端随机生成，必须非零，且在服务端保留期内唯一。HELLO 的
   Session-ID 为零；HELLO_OK 固定头中直接携带新 Session-ID。其他消息必须携带
   已建立会话的 Session-ID。

   Header-CRC 使用 CRC-16/CCITT-FALSE：初始值 0xffff，多项式 0x1021，不反射，
   不异或输出。计算范围为固定头前 28 字节；计算时不包含 Header-CRC。CRC 只
   用于快速发现随机损坏，不提供安全性。

6. TLV 正文编码

   正文是连续 TLV。每项由 Type(1)、Length(2)、Value(Length) 组成。Length 是
   无符号大端数，范围 0..65535。解析从 Body 第 0 字节开始，直到恰好消费
   Body-Length；剩余 1 或 2 字节、Value 越界或整数长度不符均为 MALFORMED_TLV。

   除 MAC 外，TLV 应按 Type 升序排列；MAC 不参与排序并且必须是最后一项。
   除明确标记为可重复的 TLV 外，
   相同 Type 出现两次是错误。未知 Type 的最高位为 0 时属于可选扩展，接收者
   跳过；最高位为 1 时属于关键扩展，接收者不认识则返回 UNSUPPORTED_TLV。

   Type  名称                 值格式       允许出现的消息
   ----  -------------------  -----------  ---------------------------------
   01    CLIENT_NAME          UTF-8        HELLO
   02    CLIENT_NONCE         16 bytes     HELLO
   03    SERVER_NONCE         16 bytes     HELLO_OK
   04    EXPIRES_MS           U64          HELLO_OK
   05    OPERATION            UTF-8        REQUEST
   06    PATH                 UTF-8        资源操作
   07    VALUE                TypedValue   资源操作
   08    VERSION              U64          资源响应
   09    EXPECTED_VERSION     U64          resource.put
   0A    COMMAND              UTF-8        command.invoke
   0B    ARGUMENTS            MAP          command.invoke/响应
   0C    IDEMPOTENCY_KEY      UTF-8        command.invoke
   0D    TOPIC                UTF-8        订阅、发布、EVENT
   0E    DATA                 TypedValue   发布、EVENT
   0F    SUBSCRIPTION         U64          订阅响应、取消订阅
   10    EVENT_SEQUENCE       U64          EVENT
   11    STATUS               U16          RESPONSE、ERROR、GOODBYE
   12    DETAIL               UTF-8        ERROR、GOODBYE
   13    MAC                  16 bytes     所有消息；必须最后出现
   14    DELIVERED_COUNT      U64          topic.publish 成功响应

   CLIENT_NAME 长度为 1..64 字节。OPERATION、COMMAND 长度为 1..64 字节。
   IDEMPOTENCY_KEY 长度为 8..128 字节。DETAIL 最大 256 字节，不应包含密钥或
   内部堆栈。整数 TLV 必须使用表中精确长度，不允许省略前导零。

7. 类型化应用值

   VALUE 和 DATA 的首字节是 Value-Type，余下字节是负载：

   00 NULL：无负载。01 FALSE：无负载。02 TRUE：无负载。
   03 I64：恰好 8 字节有符号整数。
   04 UTF8：0..65534 字节 UTF-8 文本。
   05 BYTES：0..65534 字节不透明数据。
   06 MAP：负载为 Field-ID(2)、Length(2)、Value(N) 的连续字段。
   07 LIST：负载为 Item-Length(2)、TypedValue(N) 的连续项目。

   MAP 的 Field-ID 是应用定义的无符号整数，同一 MAP 内不得重复。MAP 和 LIST
   最大嵌套深度 SHOULD 为 8，元素总数 SHOULD 不超过 1024。接收者必须先验证
   全部边界，再构造对象。比较版本或执行条件写入时，值的类型也是值的一部分；
   整数 1、文本 "1" 和单字节 BYTES 0x31 不相等。

8. 会话建立与状态机

8.1 HELLO

   HELLO 必须具有 Kind=1、Session-ID=0、CLIENT_NAME、CLIENT_NONCE 和 MAC。
   CLIENT_NONCE 恰好 16 字节，必须来自安全随机源。Transaction-ID 在本次握手
   中唯一。HELLO 不得包含业务操作 TLV。

8.2 HELLO_OK

   服务端完成语法、PSK MAC、客户端名称策略和资源限制检查后，生成 16 字节
   SERVER_NONCE、非零 Session-ID 和会话到期时间。HELLO_OK 必须复制握手事务
   ID，并包含 SERVER_NONCE、EXPIRES_MS 和 MAC。EXPIRES_MS 表示自 HELLO_OK
   发出起允许的最大空闲毫秒数，而不是绝对时钟。

   客户端验证 HELLO_OK 的事务 ID、PSK MAC 和 SERVER_NONCE 后进入 ESTABLISHED。
   验证失败必须丢弃响应；UDP 客户端可用同一 HELLO 重试，TCP 客户端应关闭连接。

8.3 会话结束

   GOODBYE 包含 STATUS 和可选 DETAIL。STATUS=0 表示正常关闭；非零表示协议方
   主动终止。TCP 发送方发送后不再创建请求，并在收到对端 GOODBYE 或 2 秒后
   关闭连接。UDP 发送方发送一次即可。服务端应将 Session-ID 和去重记录保留
   至少 60 秒，以便识别迟到的重传，但不得再执行业务。

9. 消息认证与密钥派生

   HELLO 和 HELLO_OK 使用部署 PSK。会话密钥计算为：

      SessionKey = HMAC-SHA-256(
          PSK,
          ASCII("ATP/1 session") || ClientNonce || ServerNonce ||
          Session-ID 的 8 字节大端表示)

   MAC TLV 的值为 HMAC-SHA-256 前 16 字节。计算输入为：固定头（Header-CRC
   置零，Body-Length 包含最终 19 字节 MAC TLV）|| 除 MAC TLV 外的正文。
   因此 TLV 顺序、Flags、Transaction-ID、Session-ID 和长度均受认证保护。

   发送者先排列非 MAC TLV，确定最终 Body-Length，构造 CRC 清零的固定头，计算
   MAC，附加 MAC TLV，最后计算 Header-CRC。接收者先检查长度和 CRC，再定位并
   移除最后的 MAC TLV，以相同方式计算预期 MAC，并用常量时间算法比较。

10. 请求、响应和幂等处理

   每个 REQUEST 必须有 OPERATION 和 MAC。服务端完成认证后，以
   (Session-ID, Transaction-ID) 查询去重缓存：

   a. 未找到：计算整个已认证 REQUEST 的摘要，执行操作并缓存摘要和响应。
   b. 找到且摘要相同：不得再次执行操作，直接返回原 RESPONSE 或 ERROR。
   c. 找到但摘要不同：返回 DUPLICATE_MISMATCH，并保留原缓存记录。

   UDP 重传除了设置 RETRANSMIT 外，其他字段不得变化。去重比较应忽略该标志位，
   否则合法重传会被误判。服务端至少缓存最近 256 项或最近 60 秒内的所有项目，
   以先达到的更大集合为准。有长期副作用的命令还必须按 IDEMPOTENCY_KEY 建立
   跨会话持久记录，因为客户端重启后会获得新的 Session-ID。

11. 应用操作

11.1 resource.get

   请求必须包含 OPERATION="resource.get" 和 PATH。PATH 必须以 / 开头，由
   1..16 个非空段组成；段只允许字母、数字、下划线、连字符和点；总长度不超过
   128 字节，不允许 .、..、连续斜杠或结尾斜杠。成功响应包含 STATUS=0、VALUE
   和 VERSION。不存在返回 NOT_FOUND。读取不得改变资源版本。

11.2 resource.put

   请求必须包含 OPERATION="resource.put"、PATH 和 VALUE，可带
   EXPECTED_VERSION。无条件写入创建或替换资源；新资源版本为 1，已有资源每次
   成功写入版本加 1。若带 EXPECTED_VERSION，服务端仅在当前版本完全相等时写入。
   对不存在资源，EXPECTED_VERSION=0 表示“仅当不存在时创建”。版本不符返回
   VERSION_CONFLICT，并 MAY 在 ERROR 中附带当前 VERSION。失败写入不得改变值。

11.3 resource.delete

   请求包含 OPERATION="resource.delete"、PATH，可带 EXPECTED_VERSION。成功
   删除返回 STATUS=0 和删除前 VERSION。不存在返回 NOT_FOUND。条件不符返回
   VERSION_CONFLICT。删除后的同路径新资源从版本 1 开始；部署若需要防止 ABA
   问题，应持久维护路径修订号。

11.4 command.invoke

   请求包含 OPERATION="command.invoke"、COMMAND、ARGUMENTS 和
   IDEMPOTENCY_KEY。ARGUMENTS 是 MAP。服务端先检查命令权限和参数，再执行。
   同一客户端身份和 IDEMPOTENCY_KEY 在保留期内只能表示同一命令及参数。
   参考命令 echo 原样返回 ARGUMENTS。未知命令返回 UNKNOWN_OPERATION；参数错误
   返回 BAD_REQUEST。命令是否同步完成由部署定义，但一次基础响应必须在本地
   request_timeout 内产生；长任务应返回任务资源路径供后续 resource.get 查询。

11.5 topic.subscribe 与 topic.unsubscribe

   subscribe 请求带 TOPIC。主题由 / 分隔的非空段组成，可在最后一段使用单个 *
   表示前缀匹配，例如 status/*；其他位置不得使用通配符。成功响应返回服务端
   生成的非零 SUBSCRIPTION。unsubscribe 请求带该 SUBSCRIPTION；不存在或不属于
   当前会话时返回 NOT_FOUND。订阅在会话结束时自动删除。

11.6 topic.publish

   publish 请求带 TOPIC 和 DATA，TOPIC 必须是具体主题，不能包含 *。服务端验证
   发布权限后返回 STATUS=0；响应 MAY 以 DELIVERED_COUNT 包含成功排队的订阅者
   数量。发布成功并不
   保证所有订阅者已收到 EVENT。要求持久、确认或重放的部署应另行增加扩展操作。

12. 订阅与异步事件

   EVENT 包含 SUBSCRIPTION、TOPIC、DATA、EVENT_SEQUENCE 和 MAC。每个订阅的
   EVENT_SEQUENCE 从 1 开始单调递增，不得回绕。TCP 中服务端按序写出同一订阅
   的事件；UDP 中事件可能丢失或乱序。客户端收到小于等于最近序号的事件应视为
   重复并忽略；发现序号跳跃，应读取相应资源的当前值或重新建立订阅。

   EVENT 不需要 RESPONSE。若客户端处理速度持续低于事件产生速度，TCP 服务端
   应限制每会话待发送队列；达到上限时可以发送 GOODBYE=RESOURCE_LIMIT 后断开，
   不得无限增长内存。UDP 服务端可以直接丢弃超出速率限制的事件。

13. 错误模型

   ERROR 必须复制失败 REQUEST 的 Transaction-ID，并包含 STATUS、DETAIL 和 MAC。
   DETAIL 用于诊断，不适合程序分支；客户端应依据 STATUS 决策。

    0 OK                    操作成功，仅用于 RESPONSE/GOODBYE
    1 BAD_REQUEST           缺少字段、字段取值或应用参数无效
    2 UNAUTHORIZED          身份有效但无权执行操作
    3 SESSION_EXPIRED       会话已经失效
    4 NOT_FOUND             资源、订阅或命令对象不存在
    5 VERSION_CONFLICT      条件版本与当前版本不符
    6 UNKNOWN_OPERATION     OPERATION 或 COMMAND 不受支持
    7 DUPLICATE_MISMATCH    同一事务 ID 被用于不同请求
    8 TOO_LARGE             PDU、值或集合超过限制
    9 INTERNAL              服务端意外故障；业务效果可能未知
   10 MALFORMED_TLV         TLV 截断、重复或长度错误
   11 BAD_FLAGS             保留标志非零或标志不适用于该 Kind
   12 UNSUPPORTED_TLV       无法识别的关键 TLV
   13 RESOURCE_LIMIT        会话、缓存、队列或订阅达到上限
   14 UNKNOWN_KIND          无法识别的已认证消息种类

   对 INTERNAL，客户端只有在请求具有可靠幂等语义时才应重试。对
   UNAUTHORIZED、BAD_REQUEST、MALFORMED_TLV 和 DUPLICATE_MISMATCH 不应自动
   重试。认证本身失败时不得发送 ERROR，因为无法安全确定响应对象。

14. 超时、重试和资源限制

   UDP HELLO 和 REQUEST 的初始等待时间建议为 300 ms，随后为 600 ms 和
   1200 ms，最多发送 4 次（首次加 3 次重传）。每次重传使用相同事务 ID、正文
   和会话；仅 RETRANSMIT 位改变。收到有效匹配响应后停止计时。超过次数后向
   应用报告 TIMEOUT，但不能断言服务端未执行请求。

   TCP 应用请求超时建议为 10 秒。超时可以关闭连接并重连，但若要重试有副作用
   的命令，必须复用 IDEMPOTENCY_KEY。会话空闲时长建议为 30 分钟；每收到一个
   认证有效 PDU，服务端可以刷新空闲计时。

   默认资源限制：每个 PDU 64 KiB；每个会话 64 个订阅；每个订阅 1024 个待发
   TCP 事件；每客户端每秒 100 个请求；MAP/LIST 嵌套 8 层。部署可以收紧限制，
   放宽时必须评估内存、CPU 和拒绝服务风险。

15. 安全要求

   PSK 应至少包含 128 位不可预测随机信息，不得使用设备序列号、默认口令或短
   文本。不同安全域应使用不同 PSK。服务端应支持轮换密钥，并明确旧密钥退出
   时间。nonce、Session-ID 和 Transaction-ID 必须使用适合安全用途的随机源。

   解析顺序应为：承载长度检查；固定头范围检查；CRC 检查；TLV 边界检查；会话
   查找；MAC 验证；必需字段和类型检查；权限检查；最后执行业务。任何更早阶段
   都不得分配由对端声明的无限大小内存，也不得修改资源或调用设备。

   16 字节截断 MAC 提供完整性和来源认证，不提供机密性。路径、主题、操作、值
   和通信频率均可被旁观者观察。传输敏感内容时必须在 ATP/1 外使用加密承载。
   Header-CRC 不是安全机制。服务端日志不得包含 PSK、会话密钥、完整 MAC 或敏感
   VALUE；建议记录客户端身份、事务 ID、操作、结果码和耗时。

16. 完整通信示例

16.1 资源写入

   假定会话 SID=0x2A，事务 TID=0x82。REQUEST 正文的非 MAC TLV 为：

     05 000C 7265736F757263652E707574
        Type=OPERATION, Length=12, Value="resource.put"
     06 000D 2F6C69676874732F6C6F626279
        Type=PATH, Length=13, Value="/lights/lobby"
     07 0001 02
        Type=VALUE, Length=1, Value-Type=TRUE
     13 0010 <16-byte MAC>

   服务端成功响应：STATUS TLV 为 11 0002 0000，VERSION TLV 为
   08 0008 0000000000000001。响应使用相同 TID 和 SID。

16.2 条件更新冲突

   客户端随后以 EXPECTED_VERSION=1 写入。若另一客户端已将版本更新到 2，服务端
   返回 ERROR，STATUS=5、VERSION=2、DETAIL="current version is 2"。客户端读取
   新值后决定是否再次提交，不能简单地无条件覆盖。

16.3 UDP 重传

   客户端发送 TID=0x90 的 command.invoke，服务端执行并缓存响应，但第一份响应
   在网络中丢失。300 ms 后客户端发送相同请求并设置 RETRANSMIT。服务端命中
   (SID,0x90) 缓存，直接返回原响应，不再次调用命令。若客户端因重启使用新会话，
   服务端仍通过 IDEMPOTENCY_KEY 找到持久结果。

16.4 事件缺口

   客户端订阅 status/*，获得 SUBSCRIPTION=7，依次收到 EVENT_SEQUENCE=18 和 20。
   客户端确认 19 丢失，忽略对事件历史的猜测，并调用 resource.get 获取目标设备
   当前状态。若之后又收到序号 20，则判定为重复并忽略。

17. 扩展与兼容性

   Version=1 的接收者必须拒绝其他主版本。新增可选 TLV 应使用最高位为 0 的尚未
   分配 Type；新增关键 TLV 使用最高位为 1。私有实验 Type 范围为 0x70..0x7F，
   只能在同一管理域中使用。新操作名应包含组织前缀，例如 acme.fan.calibrate，
   以降低冲突。

   扩展不得改变现有字段长度、MAC 输入、错误码含义或幂等规则。发送扩展前，
   应通过部署配置或未来的 capability 操作确认对端支持；未经确认不得发送关键
   扩展。实现必须保留未知可选 TLV 的认证效果，即跳过其业务含义，但仍将其原始
   字节纳入 MAC 验证。
